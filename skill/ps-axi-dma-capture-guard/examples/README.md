# 三个真实排查例子

> 都来自实际调试。每条只写"现象 → 查什么 → 结论方向 → 怎么验证"，不做推测。

## 例子 1 - 单次 DMA 传输很慢：先怀疑超时

- **现象**：一次传输之后要等很久才有下一次；看起来像"速度慢"，实际一直卡在等待。
- **查什么**：
  1. 中断是否正常到达（中断服务函数有没有执行）
  2. 标志位（`RxDone0` / `TxDone0` / `Error0`）在每次传输前**有没有复位**
- **结论方向**：
  - 标志没复位 ⇒ 等待会一直等满超时上限（`POLL_TIMEOUT_COUNTER`）才继续，表现就是"慢"
  - 中断没到 ⇒ 标志永远不置位，同样每次等满超时
- **验证**：复位标志 + 确认中断能到之后，单次耗时回到 ≈ `点数 ÷ 采样率`

## 例子 2 - 多次传输丢前几个数据：开关顺序反了

- **现象**：每次传输头几个点丢失，后面的数据正常。
- **查什么**：是不是**先开了前端数据输入、后开 DMA 传输**。
- **结论方向**：应当**先开 DMA 传输，再开前端的数据输入**；顺序反过来，DMA 还没准备好时前几个点就丢了。
- **验证**：改成"先开 DMA → 再开前端输入"后，多次传输前几个点不再丢失。

## 例子 3 - 条件都正常却收发都失败：查 PL 接线

- **现象**：中断正常、点数与长度也核对过，但 S2MM / MM2S 仍然都失败。
- **查什么**：PL 端接线 —— 数据流方向、tready/tvalid（AXI-Stream 握手信号）有没有接反、时钟与复位有没有接上。
- **结论方向**：PS 侧配置核对无误时，问题在 PL 侧接线；这类问题在 PS 代码里改不出来。
- **验证**：PL 接线修正后（由用户在 Vivado 里改），收发恢复正常。
